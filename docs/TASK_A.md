## 대기 중

- [ ] [TASK-069] (O) 북마크 저장 실패·경합 처리 — 조용한 실패와 데이터 유실 경로 막기
  → **배경**: 2026-08-02 코드리뷰에서 나온 것. 북마크 저장 계층이 **성공 경로만 상정하고 만들어져서**, 쓰기·읽기가 실패하면 사용자에게 알리지 않고 조용히 잘못된 상태가 됨. 웹·앱 저장 형태를 일부러 같게 맞춰둔 만큼 실패 동작도 같이 맞춰야 해서 공통 태스크
  → **웹** (`src/lib/bookmarks.ts` · `src/hooks/useBookmarks.ts`)
    - `save()`가 `setItem` 예외를 catch로 삼키고 **변경 이벤트는 그대로 발행**함. 저장이 막힌 환경(용량 초과 등)에서 버튼을 눌러도 아이콘이 안 바뀌고 안내도 없음 — 눌러도 아무 일이 없는 상태가 반복됨
    - `useBookmarks`의 `remove`가 낙관적 값을 이벤트 동기화보다 **나중에** 적용해서, 저장 실패 시 목록에서는 행이 사라진 것처럼 보이지만 새로고침하면 되살아남. 성공 경로에서는 두 값이 같아 티가 안 나 검증에서 안 걸렸음
  → **앱** (`mobile/src/lib/bookmarks.ts` · `mobile/src/hooks/use-bookmarks.ts` · `mobile/src/app/w/[slug].tsx`)
    - **읽기 실패가 파괴적 쓰기가 됨**: `loadBookmarks()`가 어떤 예외에서든 `[]`를 반환하는데, 이게 read-modify-write의 기준값으로 쓰임. `getItem`이 일시적으로 실패하거나 JSON이 깨지면 `addBookmark`가 `[새 항목]`만 저장해 **기존 북마크를 전부 날림**. 같은 이유로 `.filter(isBookmark)`에 걸린 항목은 다음 저장 때 영구 삭제됨
    - **경합**: `add`/`remove`/`syncBookmarkTitle`이 각각 읽고-고치고-쓰기라 직렬화가 없음. 문서를 열자마자 제목 동기화가 돌면서 사용자가 북마크를 해제하면, 해제가 덮어써져 다음 실행 때 되살아남
    - **연타**: `mutationFn`이 렌더 시점의 `isBookmarked`를 캡처하고 버튼에 `disabled`가 없음. 훅이 `isPending`을 돌려주는데 화면에서 안 씀 → 빠르게 두 번 누르면 두 번 다 "추가"로 동작해 최종 상태가 뒤집힘
  → **방향** (구현 전 정할 것):
    - 읽기 실패와 "비어 있음"을 **구분**할 것. 실패면 쓰기를 하지 말고 그대로 중단 — 이게 데이터 유실을 막는 핵심
    - 쓰기 실패를 호출부까지 전파하고, 최소한 토스트/문구로 사용자에게 알릴 것. 조용히 성공한 척하지 말 것
    - 앱은 낙관적 업데이트(`onMutate`)를 넣거나 `isPending` 동안 버튼을 막아 연타를 차단
    - 웹은 낙관적 값을 저장 성공을 확인한 뒤에만 적용
  → **검증**: 저장을 강제로 실패시킨 상태(용량 초과 시뮬레이션 / AsyncStorage mock 예외)에서 눌렀을 때 **사용자가 실패를 알 수 있는지**, 기존 목록이 살아남는지. 연타 시 최종 상태가 짝수/홀수에 맞는지
  → **릴리즈 영향**: 앱은 1.1.0 심사 중이라 다음 버전. 웹은 이미 배포돼 있어 고치면 바로 반영
  → **권장 모델**: Opus — 실패 시맨틱을 웹·앱 양쪽에 일관되게 설계하는 판단이 핵심이고, 잘못 고치면 오히려 데이터 유실을 늘릴 수 있음

- [ ] [TASK-070] (S) 제목에 링크가 들어간 문단의 목차 이동이 무반응인 문제
  → **배경**: 2026-08-02 코드리뷰에서 발견. **웹·앱 둘 다 동일**하며 이번 변경으로 생긴 게 아니라 원래 있던 문제(앱 목차를 시트→접이식 바로 바꾸면서 같은 증상이 그대로 따라옴)
  → **원인**: 목차용 id와 본문 heading id를 **서로 다른 입력**으로 만들고 있음
    - 목차: `headings.ts`가 `[텍스트](주소)` 문법을 벗겨낸 뒤 `slugify` → `포도-소개`
    - 본문: 웹 `MarkdownContent.tsx:134,175,179` / 앱 `structure.ts:70,111,115`가 **원본 줄을 그대로** `slugify` → `포도httpspodoexample-소개`
    - 예: `## [포도](https://podo.example) 소개`
  → **증상**: 목차 항목은 정상적으로 보이고 눌리지만 **아무 일도 안 일어남**. `getElementById(...)?.scrollIntoView()`의 `?.`가 실패를 삼켜서 오류도 안 남. 굵게/기울임/코드가 들어간 제목은 양쪽 경로가 같은 결과라 멀쩡함 — **링크가 들어간 제목만** 해당
  → **방향**: 원본 제목 → id 변환을 **함수 하나로 통일**해서 목차와 본문이 같은 걸 쓰게 할 것. 앱 `renderHtml.ts`에 이미 표시용으로 링크를 벗기는 `headingText`가 있으니 그 처리와 합치는 방향 검토
  → **주의**: id가 바뀌므로 해당 제목을 가리키던 앵커 링크가 달라짐. 다만 **지금도 깨져 있는 제목들**이라 실질 회귀는 없음. 그래도 문서 본문에 `#앵커` 링크를 쓴 곳이 있는지 확인할 것
  → **검증**: 제목에 링크가 든 문서를 만들어 웹·앱 양쪽에서 목차 항목 탭 → 실제 이동 확인
  → **권장 모델**: Sonnet — 원인과 고칠 위치가 특정돼 있고 공용 함수로 묶는 단순 작업
