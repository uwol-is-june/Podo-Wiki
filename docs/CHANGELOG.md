- [TASK-072] 로그인 후 헤더가 로그인 상태로 바로 안 바뀌던 문제 (2026-08-03)
  - 사용자 제보: "로그인해서 메인으로 오면 새로고침 전까지 헤더가 로그인 상태로 안 바뀐다"
  - 원인: `Header`가 클라이언트 컴포넌트인데 `useState(initialUser)`로 서버 값을 받고 있었음. **초기값은 최초 마운트에서만 반영되는데 Header는 레이아웃에 있어 페이지를 옮겨도 언마운트되지 않음.** 그래서 로그인 후 서버가 새 값을 내려줘도 화면은 옛 상태로 남고, 뒤늦게 도는 클라이언트 `getUser()` 왕복이 끝나야 갱신됐음
  - 실측(플레이라이트, 라이브): 메인 도착 2212ms → `auth/v1/user` 요청 2226ms → 응답 2310ms → 헤더 갱신 2344ms. **서버가 이미 아는 정보를 두고 클라이언트 왕복을 기다리는 구조**
  - 해결: 로그인·로그아웃 모두 서버 액션이 `revalidatePath('/', 'layout')`으로 레이아웃을 다시 렌더하므로 서버가 넘긴 값이 이미 정답. 레이아웃에서 `key={user?.id ?? 'anon'}`으로 사용자가 바뀔 때 Header를 새로 마운트시켜 즉시 반영. 페이지를 옮길 때마다 돌던 `getUser()` 효과는 제거(매 이동마다 인증 서버 왕복하던 낭비도 함께 해소)
  - `onAuthStateChange` 구독은 다른 탭 로그아웃·토큰 만료 대응으로 그대로 유지
  - 검증: 느린 회선(지연 400ms)에서 수정 전은 지연에 비례해 늘어나고(빠른 회선 132ms → 느린 회선 536ms), 수정 후는 그대로(33ms → 40ms). `auth/v1/user` 요청 자체가 사라짐. *(수정 전은 라이브, 수정 후는 로컬 프로덕션 빌드라 절대 수치는 직접 비교 대상이 아니며, 지연에 비례하는지 여부가 핵심 지표)*

- [TASK-069] 북마크 저장 실패·경합 처리 — 조용한 실패와 데이터 유실 경로 차단 (2026-08-03)
  - 코드리뷰에서 나온 것. 저장 계층을 성공 경로만 상정하고 만들어서, 읽기/쓰기가 실패하면 사용자에게 알리지 않고 조용히 잘못된 상태가 됐음
  - **핵심 원인은 읽기 실패를 빈 목록으로 뭉갠 것.** 그 값이 read-modify-write의 기준이 되어, 읽기가 한 번 실패하면 저장돼 있던 북마크가 전부 지워졌음(앱). `read()`가 성공/실패를 구분하고 실패 시 아무것도 쓰지 않도록 변경
  - 쓰기 실패를 호출부까지 전파 — 웹은 버튼 옆/목록 상단에 안내 문구, 앱은 Alert. 실패했는데 성공한 척 변경 이벤트를 쏘던 것도 제거
  - 웹: 낙관적 갱신을 없애고 저장 성공 시 발행되는 변경 이벤트에만 의존. 기존에는 낙관적 값이 나중에 적용돼 저장이 실패해도 목록에서 행이 사라진 것처럼 보였음
  - 앱: 모든 변경을 한 줄로 세워 직렬화(`serialize`). 문서 진입 시 제목 동기화와 사용자의 북마크 해제가 겹치면 해제가 덮어써지던 경합 해소
  - `add`/`remove` 대신 `toggleBookmark`로 통합 — 저장 여부를 **쓰기 직전에 다시 읽어** 판단하므로, 화면이 들고 있던 낡은 값으로 분기하지 않음. 앱은 `isPending` 동안 버튼도 비활성화해 연타 차단
  - `savedAt`을 파싱 가능한 날짜인지까지 검증 (`Invalid Date 저장` 렌더 방지)
  - TASK-071의 "문서 열 때마다 도는 불필요한 캐시 무효화"도 함께 해결 — `syncBookmarkTitle`이 변경 여부를 반환
  - 검증: 저장 계층을 노드에서 스텁으로 돌려 웹 12건 / 앱 7건 통과. 특히 **수정 전 코드로 경합과 데이터 유실을 실제로 재현한 뒤** 수정본에서 해소되는 것을 확인 (**앱 반영은 다음 앱 빌드/출시부터**)
